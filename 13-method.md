# 1. Зачем нужен этот файл

Когда исследуешь внутреннюю инфраструктуру, очень легко сбиться в одну из двух крайностей:

- **Слишком осторожно:** «мы не знаем ничего точно, всё гипотеза» — и в итоге вся документация превращается в поток оговорок без конкретики.  
- **Слишком смело:** «работает так-то» — хотя не проверено, и через месяц оказывается, что это была ошибка интерпретации.

Правильный подход — дисциплинированный. Каждый факт имеет уровень доказательства. Каждое утверждение либо проверено, либо помечено как гипотеза. И между «знаем точно» и «не знаем вообще» есть промежуточные состояния, которые нужно явно фиксировать.

Этот файл — методичка по такому дисциплинированному исследованию.

# 2. Главный принцип

Идти от процесса к факту, а не от догадки к догадке.

**Цепочка доказательства:**

```
process → binary → listen socket → HTTP server → route registration → handler → runtime request → response
```

Каждый шаг подтверждается отдельно:

1. Процесс существует — `ps aux`
2. Бинарник найден — `ls -l /path/to/binary`
3. Слушает порт — `ss -ltnp`
4. HTTP отвечает — `curl -i`
5. Route зарегистрирован — видно через 404/405/422
6. Handler выполняет логику — проверка через side effects
7. Ответ соответствует — проверка содержимого

Не переходить к следующему шагу, пока текущий не подтверждён.

# 3. Направление исследования

Два принципиально разных направления:

## 3.1 Top-down (от процесса к API)

Начинается с обнаружения процесса. Дальше — что это за бинарник, что он слушает, какие у него routes, что они делают.

- **Плюс:** даёт полную картину.  
- **Минус:** долго.  

**Когда использовать:** когда исследуешь незнакомый сервис с нуля.

## 3.2 Bottom-up (от поведения к процессу)

Начинается с наблюдения эффекта. Дальше — какой процесс это делает, как он запущен, что за API у него.

- **Плюс:** быстро даёт ответы на конкретные вопросы.  
- **Минус:** можно упустить общую картину.  

**Когда использовать:** когда нужно понять, кто именно делает что-то конкретное.

## 3.3 Комбинирование

Обычно оба используются вместе:

- Начинаешь top-down — обнаруживаешь сервисы  
- Дальше bottom-up — для конкретных вопросов

# 4. Пять уровней доказательства

Ключевая концепция — маркировать каждый факт уровнем.

## 4.1 ✅ runtime

**Что означает:** поведение проверено экспериментально в живой VM.

**Примеры:**

- `POST /execute` с `{}` возвращает 422 — проверено curl'ом  
- `:8085` слушается после ручного запуска daemon — проверено `ss`  
- Hive broadcast не возвращается отправителю — проверено с двумя клиентами  

**Требование:** есть конкретное наблюдение, воспроизводимое.

## 4.2 🟢 static

**Что означает:** найдено в бинарнике или исходниках, но runtime не проверялось.

**Примеры:**

- В бинарнике есть функция `get_ip::handler` — видно по symbols  
- В коде есть строка `https://api.ipify.org/` — видно по strings  
- В исходниках есть функция `record()` — видно по декомпиляции  

**Требование:** есть точный источник (symbol, строка, disasm).

## 4.3 🟡 hypothesis

**Что означает:** предположение, требующее верификации. Может быть основано на косвенных признаках.

**Примеры:**

- «40231 — это shell_port Jupyter» — из одного лога, не перепроверено на текущей VM  
- «Hive — мост к Chrome Extensions» — упоминается, но не подтверждено  
- «Флаг X влияет на Y» — логично, но не проверено  

**Требование:** явно указано, что это гипотеза, и что именно нужно для проверки.

## 4.4 ⭕ disabled

**Что означает:** предусмотрено в системе, но по умолчанию выключено.

**Примеры:**

- `container_daemon` слушает `:8085` — но только при `CUA_DD_INIT_CONTAINER_DAEMON=true`  
- Chromium CDP — но только при `CUA_DD_ENABLE_CHROME=true`  
- `offline_proxy` — но только при `START_PROXY=true`  

**Требование:** указан триггер включения.

## 4.5 ❌ disproved

**Что означает:** опровергнуто экспериментом. Раньше предполагалось — теперь знаем, что не так.

**Примеры:**

- «Rust на `:8080`» — в текущей сборке чистый Python. Опровергнуто.  
- «UI может через JS дотянуться до runtime» — `TypeError: Failed to fetch`. Опровергнуто.  
- «daemon имеет эксклюзивный сетевой путь» — runtime показал DNS fail. Опровергнуто.  

**Требование:** указано, как именно опровергнуто.

## 4.6 Промежуточные состояния

Если факт не попадает ни в одну категорию — использовать комбинации:

- 🟢 static + ✅ runtime — найдено в бинарнике и подтверждено в runtime  
- 🟢 static + 🟡 hypothesis — найдено в бинарнике, но роль в системе неясна  
- ✅ runtime (частично) — проверено только в одном сценарии  

# 5. Как исследовать новый endpoint

Обнаружили route, которого нет в документации. Что делать?

## 5.1 Шаг 1 — проверить существование

```bash
curl -i http://127.0.0.1:8085/<route>
```

**Возможные результаты:**

| Код | Что значит                          |
|-----|-------------------------------------|
| 200 | Route есть, работает без параметров |
| 400 | Route есть, но нужны параметры      |
| 404 | Route нет или путь неверный         |
| 405 | Route есть, но метод неправильный   |
| 422 | Route есть, но JSON schema не подошла |
| 500 | Route есть, backend упал            |

## 5.2 Шаг 2 — определить методы

Если 405 на GET — попробовать POST, PUT, DELETE.

```bash
for method in GET POST PUT DELETE; do
    echo "=== $method ==="
    curl -i -X $method http://127.0.0.1:8085/<route> | head -1
done
```

Не делать вывод о методе по имени route! `GET /browser/new_page` даёт 405, а `POST /browser/new_page` работает. Имя не говорит о методе.

## 5.3 Шаг 3 — проверить пустой JSON

```bash
curl -i -X POST http://127.0.0.1:8085/<route> \
    -H 'Content-Type: application/json' \
    -d '{}'
```

**Возможные результаты:**

| Код | Что значит                          |
|-----|-------------------------------------|
| 200 | Route принимает пустой JSON         |
| 422 | Route существует, schema валидируется |
| 400 | Route существует, но JSON плохой    |

Если 422 — значит route есть, нужно подобрать поля.

## 5.4 Шаг 4 — определить обязательные поля

Менять только одно поле за эксперимент. Если меняешь два сразу — не поймёшь, какое имеет значение.

**Пример:**

```bash
# Гипотеза 1: нужен "url"
curl -i -X POST http://127.0.0.1:8085/<route> \
    -H 'Content-Type: application/json' \
    -d '{"url": "https://example.com"}'

# Гипотеза 2: нужен "target"
curl -i -X POST http://127.0.0.1:8085/<route> \
    -H 'Content-Type: application/json' \
    -d '{"target": "https://example.com"}'
```

Один из них сработает, другой вернёт 422.

## 5.5 Шаг 5 — проверить успешный request

Когда schema подобрана, запустить полный запрос и зафиксировать:

- HTTP status  
- Content-Type  
- Response body  
- Response headers  
- Side effect (что изменилось в системе)  

## 5.6 Шаг 6 — проверить backend failure

Отделить разные типы ошибок:

| Ошибка | Что значит                              |
|--------|-----------------------------------------|
| 404    | route отсутствует                       |
| 405    | route есть, метод неправильный          |
| 422    | route есть, request schema неправильная |
| 500    | handler/backend failure                 |

500 может означать, что HTTP-сервер жив, но downstream (например, Chromium) недоступен.

## 5.7 Шаг 7 — записать контракт

После успешной проверки — зафиксировать:

```
Route: /browser/new_page
Method: POST
Request: {"url": "string"}
Response: {"page_html": "...", ...}
Statuses: 200, 405, 422, 500
Side effect: создание вкладки в Chromium
```

## 5.8 Пример из практики

Исследуем `/browser/new_page`:

```bash
# Шаг 1
curl -i http://127.0.0.1:8085/browser/new_page
# → 405 (route есть, но GET не подходит)

# Шаг 2
curl -i -X POST http://127.0.0.1:8085/browser/new_page
# → 415 (нужен Content-Type)

# Шаг 3
curl -i -X POST http://127.0.0.1:8085/browser/new_page \
    -H 'Content-Type: application/json' -d '{}'
# → 422 (schema не подошла)

# Шаг 4
curl -i -X POST http://127.0.0.1:8085/browser/new_page \
    -H 'Content-Type: application/json' -d '{"url":"https://example.com"}'
# → 200 (успех)

# Шаг 5: смотрим тело
# → {"page_html": "<html>...chrome-error://chromewebdata/...", ...}
```

Записываем: route существует, принимает `{"url": "string"}`, возвращает HTML. Если Chromium не запущен — `500 Received no response from the chromium instance`.

# 6. Как исследовать новый сервис

Обнаружили порт, но не знаем, что это.

## 6.1 Шаг 1 — найти процесс

```bash
ss -ltnp | grep ':<port>'
```

Вывод покажет PID и имя процесса.

```bash
ps -p <PID> -o pid,ppid,user,cmd
```

Покажет команду запуска.

## 6.2 Шаг 2 — посмотреть на бинарник

```bash
ls -la /path/to/binary
file /path/to/binary
```

Ожидаемо: ELF, размер, архитектура.

## 6.3 Шаг 3 — посмотреть на строки

```bash
strings /path/to/binary | grep -iE 'http|api|route|endpoint' | head -50
```

Это даст первичное представление о том, какие endpoints и URL встречаются в бинарнике.

## 6.4 Шаг 4 — посмотреть на символы

```bash
nm -C /path/to/binary 2>/dev/null | grep -iE 'handler|route|server' | head -50
```

Если бинарник не stripped — увидим функции. Особенно полезно для Rust (имена функций информативны).

## 6.5 Шаг 5 — проверить HTTP

```bash
curl -i http://127.0.0.1:<port>/
```

Смотрим response:

- 404 — HTTP-сервер есть, но route `/` не зарегистрирован  
- 200 — HTTP-сервер есть, root работает  
- Ошибка соединения — не HTTP, или слушает не то  

## 6.6 Шаг 6 — исследовать известные endpoints

Если в strings видны имена endpoints, попробовать их по методике из раздела 5.

## 6.7 Шаг 7 — посмотреть на окружение процесса

```bash
tr '\0' '\n' < /proc/<PID>/environ | sort
```

Это даст env-переменные, которые могут указывать на конфигурацию.

## 6.8 Шаг 8 — посмотреть на init-скрипт

Если сервис запускается через init-скрипт:

```bash
cat /usr/local/init_scripts/<service>.sh
```

Скрипт покажет флаги, env-переменные, аргументы.

# 7. Как исследовать бинарник

Если бинарник большой и информации в нём много.

## 7.1 Этап 1 — общая структура

```bash
file /path/to/binary          # тип, архитектура
ls -la /path/to/binary        # размер
readelf -h /path/to/binary    # ELF header
```

## 7.2 Этап 2 — strings

```bash
strings /path/to/binary | grep -iE '<keyword>' | sort -u
```

**Полезные группы:**

| Что искать          | Что найдёшь              |
|---------------------|--------------------------|
| `https?://`         | URL-адреса               |
| `/[a-zA-Z0-9_/-]+`  | пути, endpoints          |
| `error\|fail`       | сообщения об ошибках     |
| `api\.`             | API endpoints            |
| `ws://`             | WebSocket URLs           |

## 7.3 Этап 3 — символы

```bash
nm -C /path/to/binary 2>/dev/null | sort | less
```

Для Rust-бинарников имена функций дают очень много:

```
container_daemon::server::handlers::files::get_file_path
container_daemon::server::handlers::config::set_ip
container_daemon::offline_proxy::proxy::proxy_request
```

Из этих имён видно структуру кода.

## 7.4 Этап 4 — конкретные функции

Нашёл интересную функцию:

```bash
ADDR=$(nm -C /path/to/binary | grep -E ' t .*interesting_func$' | awk '{print $1}')
objdump -d --start-address=0x$ADDR --stop-address=$((0x$ADDR + 0x2000)) \
    /path/to/binary | less
```

Это покажет ассемблер функции. Особенно интересно для поиска:

- констант (адресов, строк)  
- вызовов других функций  
- сравнений  

## 7.5 Этап 5 — поиск XREF

Если нашёл интересную строку в strings, можно найти, где она используется:

```bash
# Найти offset строки в .rodata
strings -t x /path/to/binary | grep "https://api.ipify.org"

# Найти в disasm ссылку на этот offset
objdump -d /path/to/binary | grep -i "lea.*<offset>"
```

## 7.6 Пример

В `container_daemon` нашли строку `https://api.ipify.org/`. Нашли её использование:

```
0x602bfe: lea r13, [rip+...]     → "https://api.ipify.org/"
0x602c0c: mov ..., 0x16          → длина URL = 22
0x602c9f: call reqwest::...Client::get
```

Дальше — видно, что вызывается `reqwest::Client::get`. Значит код реально исполняется.

# 8. Как исследовать протокол

Если сервис общается по кастомному протоколу.

## 8.1 Шаг 1 — определить транспорт

- HTTP — `curl` работает  
- WebSocket — `websocat` работает  
- JSON-RPC поверх Unix socket — `socat` / Python socket  
- ZMQ — `pyzmq`  
- Custom binary — сложнее  

## 8.2 Шаг 2 — минимальный валидный пакет

Найти самое простое сообщение, которое принимается.

Например, для Hive:

```json
{"kind": "broadcast", "id": "x", "data": {}}
```

## 8.3 Шаг 3 — определить обязательные поля

Убирать по одному полю:

```json
{}                                          → reject
{"kind": "broadcast"}                       → reject
{"kind": "broadcast", "id": "x"}            → reject
{"kind": "broadcast", "id": "x", "data": {}} → accept
```

Отсюда видно: все три поля обязательны.

## 8.4 Шаг 4 — определить типы полей

Менять тип одного поля:

```json
{"kind": "broadcast", "id": "x", "data": {}}       → accept
{"kind": "broadcast", "id": 1, "data": {}}         → reject (id должен быть string)
{"kind": "broadcast", "id": "x", "data": "HELLO"}  → accept (data — любой JSON)
{"kind": "broadcast", "id": "x", "data": null}     → accept
```

## 8.5 Шаг 5 — определить семантику полей

Проверить гипотезы:

- Является ли `kind` дискриминатором? (в Hive — нет, просто строка)  
- Является ли `id` коррелятором? (в Hive — просто сохраняется)  
- Что делает `data`? (в Hive — передаётся как есть)  

## 8.6 Шаг 6 — определить поведение

Проверить важные свойства:

- Возвращается ли сообщение отправителю? (в Hive — нет)  
- Что происходит при нескольких клиентах? (в Hive — broadcast всем, кроме отправителя)  
- Что происходит при нуле других клиентов? (в Hive — сообщение в никуда)  

## 8.7 Шаг 7 — определить внутренние сущности

Найти:

- UUID / сессии / клиенты  
- Какие поля добавляются сервером (в Hive — `from`)  
- Какие поля приходят от клиента (в Hive — `kind`, `id`, `data`)  

# 9. Как корректно описывать находки

## 9.1 Три уровня детализации

**Уровень 1 — обнаружено**

```
Endpoint /foo существует.
```

**Уровень 2 — контракт**

```
Endpoint /foo существует.
Принимает POST с {"bar": "string"}.
Возвращает {"status": "ok"}.
При пустом JSON — 422.
```

**Уровень 3 — поведение**

```
Endpoint /foo существует.
Принимает POST с {"bar": "string"}.
Возвращает {"status": "ok"}.
При пустом JSON — 422.
Side effect: создаётся запись в таблице X.
При повторном вызове — идемпотентно.
Ошибки:
  400 — при bar длиннее 256 символов
  500 — при недоступности backend Y
```

Уровень детализации зависит от того, что проверено. Не придумывать уровень 3, если проверен только уровень 1.

## 9.2 Не смешивать уровни

Нельзя писать:

> Endpoint /foo, вероятно, принимает {"bar": "string"} и возвращает {"status": "ok"}.

Это смешение гипотезы (вероятно) с контрактом (принимает). Правильно:

> 🟡 Endpoint /foo существует. 🟢 По имени в бинарнике похоже, что принимает строку. ✅ runtime-контракт не восстановлен.

## 9.3 Указывать источник

Каждый факт должен иметь источник:

- ✅ runtime + как проверено  
- 🟢 static + где найдено (symbol, строка)  
- 🟡 + на чём основано  

Без источника — не факт, а догадка.

# 10. Типичные ошибки

## 10.1 Слишком много оговорок

**Плохо:**

> Мы не уверены, но, возможно, endpoint принимает код. Хотя мы не проверяли. Может быть, это не так. Схема могла измениться.

**Хорошо:**

> ✅ POST /execute принимает {"code": "string"}. Проверено на {"code": 123} → 422.

## 10.2 Выводы по именам файлов

В бинарнике есть файл `get_state.rs`. Это не значит, что HTTP-route `/browser/get_state` существует.

В нашем случае: файл `get_state.rs` есть, но route `/browser/get_state` → 404.

**Правило:** имя файла-исходника ≠ HTTP-путь.

## 10.3 Предположение о методе

Имя `/browser/new_page` намекает на POST. Но это не факт, пока не проверено.

Проверяем:

```bash
curl -i -X GET http://127.0.0.1:8085/browser/new_page   # → 405
curl -i -X POST http://127.0.0.1:8085/browser/new_page  # → 200
```

## 10.4 Игнорирование отрицательных результатов

Отрицательные результаты так же важны:

- `GET /browser/get_state` → 404 — доказательство, что route не зарегистрирован  
- `POST /execute {}` → 422 — доказательство, что schema валидируется  
- UI → `127.0.0.1:8765` → `Failed to fetch` — доказательство, что этот путь не работает  

Их надо фиксировать.

## 10.5 Смешение env-переменных

`HTTP_PROXY` есть в supervisor env, но не в kernel env. Это разные окружения. Нельзя делать вывод «proxy настроен» — только «proxy настроен для процесса X, не для процесса Y».

## 10.6 Использование pid из другого лога

PID'ы меняются между запусками VM. PID 190 из лога №6 и PID 225 из лога №13 — разные инстансы. Не путать.

## 10.7 Ожидание статичного состояния

Порты Jupyter, PID'ы, содержимое `/tmp` — всё меняется. Не хардкодить. Каждый раз читать актуальное состояние.

# 11. Что НЕ следует делать

## 11.1 Придумывать JSON schema

Если schema не восстановлена — не писать `{"x": int, "y": int}` «по логике». Правильно — пометить 🟡 schema не восстановлена.

## 11.2 Считать route доступным без проверки

Наличие route в бинарнике — это 🟢. Доступность — ✅. Между ними пропасть.

## 11.3 Путать сервисы

`:8080`, `:1384`, `:8085`, `:50939`, `:9222`, `:9999` — это разные сервисы. Нельзя делать вывод «API X работает, значит Y работает» — это независимые компоненты.

## 11.4 Смешивать «не работает» и «не проверено»

- ❌ disproved — проверено, что не работает.  
- 🟡 — не проверено.  
- ⭕ disabled — выключено по умолчанию.  

Это три разные категории. Не путать.

## 11.5 Один эксперимент — один факт

Если меняешь сразу много параметров, невозможно понять, что на что повлияло. Правило: один параметр — один эксперимент.

## 11.6 Использовать ненадёжные источники

Публичная документация Jupyter рассказывает общую модель Jupyter. Наша внутренняя реализация может отличаться. Всё, что относится к нашей VM — только из наблюдений внутри VM.

# 12. Практические приёмы

## 12.1 Быстрая проверка HTTP-статусов

```bash
for code in 200 400 404 405 422 500; do
    :  # проверять конкретный случай
done
```

Или:

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8085/<route>
```

Только код, без тела — удобно для скриптов.

## 12.2 Просмотр только заголовков

```bash
curl -I http://127.0.0.1:8085/<route>
# или
curl -i -X GET ... | head -20
```

## 12.3 Логирование запроса и ответа

```bash
curl -v http://127.0.0.1:8085/<route> 2>&1 | less
```

`-v` покажет:

- запрос полностью (метод, заголовки, тело)  
- ответ полностью (статус, заголовки, тело)  
- TLS handshake (если есть)  

## 12.4 Проверка порта

```bash
# Слушает ли кто-то порт
ss -ltnp | grep ':<port>'

# Есть ли соединение с портом
ss -tnp | grep ':<port>'
```

## 12.5 Проверка процесса

```bash
# Процесс жив
ps -p <PID> -o pid,ppid,user,cmd

# Env процесса
tr '\0' '\n' < /proc/<PID>/environ | sort

# Открытые файлы
ls -l /proc/<PID>/fd

# Namespace
readlink /proc/<PID>/ns/net
readlink /proc/<PID>/ns/mnt
```

## 12.6 Проверка бинарника

```bash
# Что за бинарник
file /path/to/binary

# Зависимости
ldd /path/to/binary

# Символы
nm -C /path/to/binary | head -100

# Строки
strings /path/to/binary | head -100
```

## 12.7 Дизассемблирование функции

```bash
# Найти адрес функции
ADDR=$(nm -C /path/to/binary | grep ' t .*function_name$' | awk '{print $1}')

# Дизассемблировать
objdump -d --start-address=0x$ADDR --stop-address=$((0x$ADDR + 0x1000)) \
    /path/to/binary | less
```

## 12.8 Отслеживание HTTP-запросов

Если хочется посмотреть, что реально отправляется:

```bash
# В одном терминале — слушать
socat -v TCP-LISTEN:9999,reuseaddr,fork SYSTEM:'echo HTTP/1.1 200 OK; echo'

# В другом — отправлять
curl http://127.0.0.1:9999/foo
```

Покажет сырые байты запроса и ответа.

# 13. Чек-лист перед записью факта

Перед тем как записать утверждение в документацию, ответить на вопросы:

1. Уровень доказательства? ✅ / 🟢 / 🟡 / ⭕ / ❌  
2. Источник? Где именно найдено (лог, symbol, runtime)?  
3. Проверено на текущей VM? Или из старого лога?  
4. Воспроизводимо? Можно ли повторить эксперимент?  
5. Есть ли противоречия? С другими фактами?  
6. Уровень детализации? Обнаружено / контракт / поведение?  

Только после ответа — записывать.

# 14. Формат записи в документацию

## 14.1 Для endpoint

```markdown
### `POST /example/route`

**Назначение:** краткое описание.

**Request:** `{"field": "type"}`

**Response:** `{"result": "type"}`

**Статусы:**
- `200` — успех
- `422` — schema не подходит

**Side effect:** что меняется в системе.

**Источник:** ✅ runtime, проверено curl'ом.

**Ограничения:** что не работает.
```

## 14.2 Для поля

```markdown
| Поле | Тип | Обязательное | Описание | Источник |
|---|---|---|---|---|
| `code` | string | ✅ | Python-код для выполнения | ✅ runtime |
| `timeout` | float | ✅ | Таймаут в секундах | ✅ runtime |
```

## 14.3 Для гипотезы

```markdown
🟡 Гипотеза: `40231` — это shell_port Jupyter.

Обоснование: упоминается в connection file в логе №1.

Что нужно для проверки: прочитать актуальный connection file.
```

## 14.4 Для отрицательного результата

```markdown
❌ `GET /browser/get_state` → 404.

Опровергнуто runtime. Файл `get_state.rs` существует, но HTTP-route не зарегистрирован.
```

# 15. Работа с противоречиями

Иногда два факта противоречат друг другу.

## 15.1 Что делать

1. Не игнорировать. Противоречие — сигнал, что что-то упущено.  
2. Зафиксировать оба. Не «исправлять» один факт другим.  
3. Найти причину. Возможно, разные сборки, разные VM, разные режимы.  

## 15.2 Пример

Лог №1: «Rust/Tokio на `:8080`».  
Лог №7: «Чистый Python на `:8080`».

Противоречие? Не обязательно. Возможно, полиморфизм — в разных сборках разные реализации.

**Правильная запись:**

> `:8080` может быть реализован как на Rust (Tokio), так и на Python (FastAPI). Спецификация OpenAPI одинакова. В текущей сборке — Python. 🟡

## 15.3 Не смешивать

Нельзя писать «сервер на `:8080` — Rust». Это усреднение противоречий, которое никого не устраивает.

Правильно — зафиксировать оба наблюдения с контекстом.

# 16. Итог

## 16.1 Главные принципы

1. Идти от процесса к факту. Не от догадки.  
2. Каждому факту — уровень доказательства. ✅ / 🟢 / 🟡 / ⭕ / ❌.  
3. Один эксперимент — один параметр.  
4. Отрицательные результаты важны.  
5. Не путать сервисы.  
6. Не придумывать schema.  
7. Источник обязателен.  
8. Противоречия не сглаживать, а фиксировать.  

## 16.2 Что это даёт

Документация, в которой:

- каждое утверждение имеет основание  
- граница между «знаем» и «предполагаем» — явная  
- будущий читатель не тратит время на перепроверку уже проверенного  
- отрицательные результаты экономят время (не пробовать то, что не работает)  

## 16.3 Чего это не даёт

Это не даёт «истину в последней инстанции». Исследование продолжается. Часть фактов будет уточнена, часть опровергнута. Но благодаря явным уровням доказательства — уточнения будут точечными, а не революционными.

## 16.4 Главная мысль

Документация — это не набор фактов, а карта с отмеченными зонами уверенности и неуверенности.

Правильно составленная карта помогает ориентироваться. Неправильно составленная — вводит в заблуждение.

Дисциплина в уровнях доказательства — это то, что отличает первое от второго.
