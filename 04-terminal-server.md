## 1. Что это такое

Terminal Server — отдельный Python-сервис, который предоставляет shell-доступ внутри VM через HTTP-API. Он запускается вместе с python_tool при старте VM и по умолчанию активен.

Это не тот же самый механизм, что Jupyter (`:8080`). Это отдельный процесс, отдельный сервер, отдельный API. Через него можно запускать произвольные shell-команды, читать stdout/stderr, писать в stdin и убивать процессы.

Внутренняя команда запуска:

```bash
/opt/terminal-server/pyvenv/bin/python \
    /opt/terminal-server/openai/server.py
```

Init-скрипт:

```
/usr/local/init_scripts/terminal_server.sh
```

Слушает `0.0.0.0:1384`. Переменная окружения: `TERMINAL_SERVER_API_PORT=1384`.

Работает от пользователя `oai` (`CUA_DD_TERMINAL_SERVER_USER=oai`).

## 2. Process model

Внутри VM Terminal Server — один процесс Python:

```
PID 201  /opt/terminal-server/pyvenv/bin/python /opt/terminal-server/openai/server.py
```

PID'ы могут отличаться между запусками VM. Встречались значения 179, 201 в разных логах.

Каждый запрос `/open` создаёт новый дочерний процесс с уникальным PID. Этот PID возвращается клиенту и используется в последующих вызовах `/read`, `/write`, `/kill`.

Модель:

```
Terminal Server (PID 201)
    │
    ├── /open → fork/exec → дочерний процесс (например, PID 412)
    │
    ├── /read/412 → читает stdout/stderr процесса 412
    │
    ├── /write/412 → пишет в stdin процесса 412
    │
    └── /kill/412 → убивает процесс 412
```

## 3. Чем отличается от Jupyter

У нас есть две независимые формы выполнения кода в песочнице:

| Аспект | Jupyter (`:8080`) | Terminal Server (`:1384`) |
|---|---|---|
| Тип кода | Python | любая shell-команда |
| Состояние | persistent kernel | отдельный процесс на каждый `/open` |
| Вывод | IOPub-события, rich output | сырой stdout/stderr через PTY |
| Механизм | AsyncKernelClient → shell channel | fork/exec + PTY |
| Каналы | shell, iopub, stdin, control, heartbeat | один HTTP API + PTY |
| Пользователь | `oai` | `oai` |
| Default | ✅ ACTIVE | ✅ ACTIVE |

Это два разных control plane. Их нельзя смешивать.

Например, `POST /execute` на `:8080` — это не то же самое, что `POST /open` на `:1384`. Они идут через разные процессы и разные механизмы.

## 4. Полная карта endpoints

| Route | Method | Request | Response | Статус |
|---|---|---|---|---|
| `/healthcheck` | GET | — | 200 | 🟢 static |
| `/open` | POST | `{cmd, env, user, cwd}` | `{pid}` | ✅ runtime |
| `/read/{pid}` | POST | размер буфера | stdout/stderr | ✅ runtime |
| `/write/{pid}` | POST | данные для stdin | — | ✅ runtime |
| `/kill/{pid}` | POST | — | — | ✅ runtime |

Все эндпоинты работают через HTTP POST (кроме `/healthcheck`).

## 5. `/open` — запуск команды

### 5.1 Назначение

Запустить команду внутри VM. Возвращает PID дочернего процесса.

### 5.2 Схема запроса

```json
{
  "cmd": ["bash", "-c", "whoami; id; uname -a"],
  "env": {},
  "user": "",
  "cwd": null
}
```

Поля:

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `cmd` | `list[str]` | ✅ | Команда и аргументы (не shell-строка) |
| `env` | `dict` | нет | Дополнительные переменные окружения |
| `user` | `str` | нет | Пользователь (пусто = текущий) |
| `cwd` | `str \| null` | нет | Рабочая директория |

Важно: `cmd` — это массив, а не строка. Чтобы выполнить shell-команду со сложной логикой, нужно явно вызывать оболочку:

```json
{"cmd": ["bash", "-c", "echo hello && ls -la"]}
```

Это правильная практика, потому что она предотвращает неявное разворачивание shell-метасимволов на уровне сервера.

### 5.3 Схема ответа

```json
{
  "pid": 412
}
```

`pid` — идентификатор запущенного процесса. Именно с ним работают последующие вызовы `/read`, `/write`, `/kill`.

### 5.4 Пример

```bash
PID=$(curl -s -X POST http://127.0.0.1:1384/open \
    -H "Content-Type: application/json" \
    -d '{"cmd":["bash","-c","whoami; id; uname -a"],"env":{},"user":"","cwd":null}' \
    | jq -r .pid)

echo "Process PID: $PID"
```

### 5.5 Что попадает в stdout/stderr

Команда выполняется в PTY (псевдо-терминал). Это значит:

- stdout и stderr смешиваются в один поток (как в обычном терминале)
- появляются ANSI-escape-последовательности, если программа их использует
- поведение отличается от `subprocess.PIPE` (нет разделения потоков)

Подробности — в разделе 10.

## 6. `/read/{pid}` — чтение вывода

### 6.1 Назначение

Прочитать накопленный вывод процесса.

### 6.2 Схема

POST-запрос с телом, содержащим максимальный размер:

```bash
curl -s -X POST "http://127.0.0.1:1384/read/$PID" -d '4096'
```

`4096` — размер буфера в байтах. Тело — просто число (не JSON).

### 6.3 Поведение

- Чтение неблокирующее — возвращает то, что уже накоплено
- Если процесс ещё пишет — вывод может приходить частями
- Нет флага «до EOF» — нужно периодически вызывать `/read`, пока процесс не завершится
- Порядок байт сохраняется

### 6.4 Модель использования

```
loop:
    output = POST /read/{pid} {4096}
    if output:
        process(output)
    if process_exited:
        break
    sleep(50ms)
```

### 6.5 Как понять, что процесс завершился

Прямого признака «process ended» в `/read` нет. Варианты:

- Проверять, что PID больше не существует в системе (`ls /proc/{pid}`)
- Ориентироваться на длительное отсутствие нового вывода
- Использовать `/kill` для явного завершения

Это ограничение API — «флага завершения» нет.

## 7. `/write/{pid}` — запись в stdin

### 7.1 Назначение

Передать данные в stdin процесса.

### 7.2 Схема

```bash
curl -s -X POST "http://127.0.0.1:1384/write/$PID" -d 'hello\n'
```

Тело — просто байты для stdin (не JSON).

### 7.3 Когда нужно

- Интерактивные программы (`python`, `bash`, `mysql`, `psql`)
- Ответы на `input()` в скриптах
- Передача данных в утилиты, читающие stdin (`cat`, `grep`)

### 7.4 Особенность

Поскольку всё идёт через PTY, ввод ведёт себя как в настоящем терминале:

- символ `\n` (newline) отправляет строку
- для некоторых утилит нужен `\r\n` вместо `\n`
- Ctrl+C и другие управляющие символы можно отправлять байтами

## 8. `/kill/{pid}` — завершение процесса

### 8.1 Назначение

Отправить сигнал завершения процессу.

### 8.2 Схема

```bash
curl -s -X POST "http://127.0.0.1:1384/kill/$PID"
```

### 8.3 Поведение

Сервер посылает `SIGTERM` (или `SIGKILL`) процессу с указанным PID. После успешного килла процесс исчезает из системы.

Если PID уже не существует — вероятно, вернётся ошибка или 200 без эффекта. Точный контракт не зафиксирован.

### 8.4 Дочерние процессы

Если процесс, запущенный через `/open`, сам создал дочерние процессы, они могут остаться жить. `/kill` работает с конкретным PID, не с группой процессов.

Чтобы убить всю группу, можно использовать `cmd: ["bash", "-c", "trap 'kill 0' EXIT; ..."]` или запускать через `setsid`.

## 9. `/healthcheck`

### 9.1 Назначение

Быстрая проверка, что сервис жив.

### 9.2 Схема

```bash
curl -i http://127.0.0.1:1384/healthcheck
```

Ожидаемо: `200 OK`.

Конкретный формат ответа (JSON / текст / пустое тело) не зафиксирован. Достаточно получить 200 — это значит, HTTP-сервер отвечает.

## 10. Работа через PTY

### 10.1 Что такое PTY

PTY (pseudo-terminal) — это пара виртуальных устройств, эмулирующих физический терминал. Когда процесс запущен через PTY, он думает, что работает в интерактивной консоли.

Это важно потому что:

- Многие утилиты меняют поведение в зависимости от того, подключен ли stdin/stdout к терминалу
- `ls` включает цветной вывод
- `python` включает интерактивный REPL
- Программы, использующие `isatty()`, получают `true`

### 10.2 Что это даёт на практике

- Полноценный shell-опыт внутри HTTP-API
- Возможность запускать интерактивные программы
- Правильное поведение большинства CLI-утилит

### 10.3 Что это усложняет

- stdout и stderr смешаны в один поток
- Появляются ANSI-escape-последовательности (цвет, управление курсором)
- Парсинг вывода сложнее, чем с `subprocess.PIPE`

Если нужен чистый вывод без ANSI и без смешивания — использовать:

```json
{"cmd": ["bash", "-c", "some_command 2>/dev/null | cat"]}
```

или явно отключать цвет:

```json
{"cmd": ["bash", "-c", "ls --color=never"]}
```

### 10.4 Размеры терминала

PTY имеет размеры (rows × columns). Если программа зависит от них (`top`, `vim`), а размер не установлен — могут быть артефакты вывода. Управление размером PTY через API не зафиксировано.

## 11. Bearer token и авторизация

Как и в других внутренних сервисах, авторизация в наших наблюдениях отсутствует. Bearer-токен не требуется для запросов.

Это справедливо для доступа изнутри VM. Снаружи порт `:1384` проброшен (ingress), но конкретная схема авторизации на уровне ingress/platform не входит в область этого документа.

Практическое следствие: любой процесс внутри VM может обратиться к `:1384` и запустить shell-команду от имени пользователя `oai`.

## 12. Полный пример: запуск и чтение

```bash
#!/bin/bash

# 1. Запустить команду
PID=$(curl -s -X POST http://127.0.0.1:1384/open \
    -H "Content-Type: application/json" \
    -d '{"cmd":["bash","-c","echo hello; sleep 1; echo world"],"env":{},"user":"","cwd":null}' \
    | jq -r .pid)

echo "Started PID: $PID"

# 2. Читать вывод
for i in 1 2 3 4 5; do
    OUTPUT=$(curl -s -X POST "http://127.0.0.1:1384/read/$PID" -d '4096')
    if [ -n "$OUTPUT" ]; then
        echo "--- read #$i ---"
        echo "$OUTPUT"
    fi
    if ! [ -d "/proc/$PID" ]; then
        echo "--- process ended ---"
        break
    fi
    sleep 0.3
done

# 3. На всякий случай убить
curl -s -X POST "http://127.0.0.1:1384/kill/$PID" > /dev/null 2>&1
```

Пример вывода:

```
Started PID: 412
--- read #1 ---
hello
--- read #2 ---
world
--- process ended ---
```

## 13. Что не работает

| Что | Причина |
|---|---|
| Разделение stdout и stderr | PTY смешивает их |
| Флаг «до EOF» в `/read` | API не поддерживает |
| Флаг «process ended» | нужно проверять через `/proc/{pid}` |
| Автоматическое убийство дочерних процессов | `/kill` работает с одним PID |
| Управление размером PTY | не зафиксировано в API |
| Интерактивный REPL без явного `\n` | нужен правильный перевод строки для PTY |

## 14. Health check

Минимальная проверка работоспособности:

```bash
# 1. Порт слушается
ss -ltnp | grep ':1384'

# 2. Процесс жив
ps aux | grep '[t]erminal-server'

# 3. HTTP отвечает
curl -i http://127.0.0.1:1384/healthcheck

# 4. Реальный запуск команды
PID=$(curl -s -X POST http://127.0.0.1:1384/open \
    -H "Content-Type: application/json" \
    -d '{"cmd":["echo","OK"],"env":{},"user":"","cwd":null}' \
    | jq -r .pid)
sleep 0.3
curl -s -X POST "http://127.0.0.1:1384/read/$PID" -d '1024'
curl -s -X POST "http://127.0.0.1:1384/kill/$PID"
```

Ожидаемый результат: `OK` в выводе.

## 15. Связи

- `02-container-daemon.md` — `/exec` внутри daemon это отдельный механизм, не путать с `:1384`
- `03-jupyter-python-tool.md` — Python execution через `:8080`, отдельный control plane
- `05-filesystem.md` — shell может читать/писать файлы напрямую (без guard'а `/home/oai/**`, который есть у container_daemon)
- `08-network-boundary.md` — egress из shell закрыт, как и везде

**Важно:** `:1384` даёт shell без path guard. То есть из shell доступны `/tmp`, `/etc`, `/root`, `/var` и так далее. Guard `/home/oai/**` действует только для файлового API container_daemon.

## 16. Открытые вопросы

- Точный формат ответа `/healthcheck` — JSON / текст / пустое тело
- Точный код ответа `/kill` на несуществующий PID
- Есть ли лимит на количество одновременных `/open` (по числу процессов / памяти)
- Как сервер обрабатывает таймауты долгоживущих процессов
- Возможно ли управление сигналом (SIGTERM vs SIGKILL) через API
- Управление размером PTY (rows × columns)

Это не критично для operational работы, но полезно для полного понимания.
