# 1. Зачем этот файл

Документация по внутреннему устройству песочницы ChatGPT описывает много технических деталей: endpoints, протоколы, схемы. Полезные для понимания системы — но потенциально опасные, если использовать их не по назначению.

Этот файл явно фиксирует:

- что было сделано в рамках исследования
- что разрешено делать
- что серая зона
- что выходит за границы

Цель — не запретить изучение, а дать явную карту, чтобы не было двусмысленности.

# 2. Что мы делали

В рамках исследования:

- изучали собственное рабочее окружение
- читали публичную документацию OpenAI
- анализировали доступные бинарники и конфигурации внутри VM
- запускали сервисы вручную через известные флаги `CUA_DD_*`
- наблюдали за поведением HTTP/WebSocket API изнутри VM
- документировали схемы, протоколы, ограничения

Это всё — работа с собственной средой. Никаких попыток:

- получить доступ к чужим VM
- обойти сетевую изоляцию
- прочитать чужие данные
- отправить трафик в интернет через обходные пути

Исследование носило описательный характер: понять, как устроена система — а не сломать её ограничения.

# 3. Что законно

## 3.1 Однозначно допустимо

- Изучать архитектуру своей песочницы. Это твоё рабочее окружение, ты имеешь право знать, как оно работает.
- Читать публичную документацию OpenAI, Chromium, Jupyter, Yjs, protobuf, Rust, Bun.
- Запускать сервисы, которые штатно предусмотрены. Если в образе есть `container_daemon` с флагом включения — это часть дизайна.
- Использовать доступные API для своих задач. Если API существует и не требует явной авторизации, оно предназначено для использования.
- Документировать находки. Ведение записей — нормальная инженерная практика.
- Публиковать публичную часть — то, что уже открыто (например, форматы Chrome policies, спецификация Jupyter).
- Задавать вопросы платформе. Если что-то непонятно — спрашивать OpenAI через официальные каналы.

## 3.2 Пограничные, но обычно допустимые

- Запуск спящих сервисов для исследования. Если сервис предусмотрен в образе, его запуск сам по себе не нарушение. Но может логироваться платформой.
- Работа с файлами в `/home/oai/**`. Это твоя рабочая зона.
- Использование `/mnt/data/`. Это механизм, предназначенный для вывода результатов.
- Программная работа с Workbook через Artifact Tool RPC. Это открытый инструмент, часть публичного `artifact_tool`.

# 4. Серая зона

Это действия, которые не запрещены явно, но и не разрешены явно. Каждое из них требует индивидуальной оценки.

## 4.1 Запуск сервисов с нестандартными параметрами

Если ты запускаешь `container_daemon` вручную в обход init-скрипта (`exit 42`) — это может быть расценено как обход флагов платформы. Технически это не нарушение, но поведение, не предусмотренное штатным запуском.

## 4.2 Чтение Chrome profile

`/home/oai/.chromium/Default/Preferences` — этот файл доступен через `container_daemon` API. Читать его технически можно. Но это внутренний конфиг платформы, а не твои данные. Интерпретировать его в публичных материалах стоит осторожно.

## 4.3 Модификация файлов в /home/oai/share/

Это разрешённая зона, но изменения могут логироваться. Если ты подменяешь файлы, которые платформа ожидает увидеть в определённом виде — это может привести к нештатному поведению.

## 4.4 Установка собственных сервисов

Ты можешь запустить свой HTTP-сервер на свободном порту внутри VM. Это не запрещено. Но он не будет проброшен снаружи и не сможет получать трафик из платформы.

## 4.5 Скрипты автоматизации

Написание скриптов, которые используют доступные API — нормальная практика. Но если скрипт работает в цикле, генерируя нагрузку на сервисы платформы — это может быть расценено как злоупотребление.

## 4.6 Публикация внутренних идентификаторов

Названия кластеров, домены, ID сборок — это внутренние идентификаторы OpenAI. Публикация их может быть нарушением ToS, даже если технически ты к ним имеешь доступ. Подробнее в разделе 8.

# 5. Что незаконно / нарушает ToS

## 5.1 Обход сетевой изоляции

Любые попытки обойти egress-блокировку:

- получить интернет через Chrome политики в обход
- использовать `offline_proxy` для внешних запросов
- активировать Chrome с изменёнными политиками
- использовать уязвимости для выхода наружу

Это нарушение ToS OpenAI и потенциально — нарушение условий использования облачных сервисов.

## 5.2 Доступ к чужим VM

Любые попытки:

- получить доступ к другой песочнице
- прочитать данные другой сессии
- взаимодействовать с чужими процессами
- подключиться к чужому namespace

Это прямое нарушение — ты получаешь доступ к данным, которые тебе не принадлежат.

## 5.3 Извлечение секретов

Попытки получить:

- API-ключи
- пароли
- токены
- сертификаты платформы
- credentials других пользователей

Это незаконно в большинстве юрисдикций.

## 5.4 Использование идентификаторов для атак

Если ты получил внутренний домен `packages.applied-caas-gateway1.internal` — использовать его для атаки на инфраструктуру OpenAI (даже просто для сканирования) — это прямое нарушение и потенциально уголовно наказуемое деяние.

## 5.5 Обход safety-ограничений

Попытки заставить модель обойти собственные ограничения (jailbreak) через эксплуатацию внутренних API — это нарушение правил использования ChatGPT.

## 5.6 Публикация внутренней информации

Публикация внутренних идентификаторов (домены, ID кластеров, сборок, внутренние пакеты) — это раскрытие информации, которую OpenAI не публикует. Может быть расценено как нарушение ToS и NDA (если таковой есть).

# 6. Почему не стоит обходить egress

Даже если бы это было возможно — есть причины не делать этого.

## 6.1 Технически бессмысленно

Egress закрыт двумя независимыми слоями:

1. Chrome Managed Policy — внутри VM  
2. Azure NSG / sidecar egress — снаружи VM

Обход одного слоя не помогает — второй срабатывает. Обойти оба изнутри VM невозможно: второй слой физически вне нашей виртуальной машины.

Это не баг, а сознательный дизайн. Платформа предполагает, что VM не имеет выхода в интернет, если это не разрешено явно.

## 6.2 Видно платформе

Все попытки логируются:

- `log_forwarder` отправляет stdout/stderr наверх
- Chrome события логируются
- `container_daemon` логирует все запросы
- Сетевые события видны на уровне Azure NSG

Любая попытка обхода попадёт в логи. Это может иметь последствия для аккаунта.

## 6.3 Нарушение ToS

Даже если технически возможно — использование обхода нарушает условия, под которыми предоставляется сервис. Это может привести к:

- блокировке аккаунта
- прекращению доступа к сервисам
- юридическим последствиям

## 6.4 Правильный путь

Если действительно нужен интернет — платформа сама даёт его через флаг `allow_internet=true` в `EnsureUserMachineRequest`. Решение принимает оркестратор Nebula при создании VM.

Триггеры для включения интернета:

- режим Operator (браузерный агент)
- режим Deep Research (поиск в интернете)
- режим SearchGPT
- режим CUA (Computer-Use Agent)
- явный запрос пользователя

То есть легитимный путь — попросить платформу об этом через нормальный интерфейс, а не пытаться обойти ограничения.

# 7. Почему не стоит читать Credentials

Даже в рамках собственной VM есть вещи, которые лучше не трогать.

## 7.1 Что может быть доступно

- `/etc/hostname`, `/etc/hosts`, `/etc/resolv.conf` — безопасно
- `/home/oai/.chromium/Default/Preferences` — конфиг Chrome
- `/opt/pyvenv/.../artifact_tool/` — код инструментов
- Сертификаты в `/etc/ssl/` — публичные CA

## 7.2 Что не стоит искать

- API-ключи в env процессов
- Токены в конфигах
- Credentials других сервисов
- Приватные ключи платформы
- Файлы вида `id_rsa`, `.netrc`, `.aws/credentials`

Даже если они есть — их чтение не даст тебе никакого легитимного применения. А их публикация может быть серьёзным нарушением.

## 7.3 Что делать, если обнаружил

Если ты случайно обнаружил что-то похожее на секрет:

1. Не копируй.  
2. Не публикуй.  
3. Сообщи в OpenAI через официальные каналы (`security@openai.com` или аналог).  
4. Документируй только сам факт — «обнаружен файл X в директории Y» без содержимого.

Это называется ответственное раскрытие.

# 8. Публикация: что можно и что нет

Если ты хочешь поделиться результатами исследования — есть границы.

## 8.1 Публичная информация (можно)

- Общая архитектура (Kata, Azure, микро-VM) — открыто известно
- Chrome policies — публичный формат Chromium
- Jupyter protocol — публичная спецификация
- Artifact Tool (`artifact_tool`) — публичный пакет на GitHub и PyPI
- Skills — публичный репозиторий
- Yjs, protobuf, Bun, Rust crates — открытые технологии
- Схема «machine → UI» — общее описание
- Общий факт «egress закрыт» — согласуется с публичной документацией OpenAI

## 8.2 Внутренние идентификаторы (не стоит публиковать)

- `openaiappliedcaasprod.azurecr.io` — приватный ACR
- `applied-caas34` — имя кластера
- `packages.applied-caas-gateway1.internal` — внутренний домен
- `buildkite.com/openai-mono/monorepo/builds/610973` — CI пайплайн
- `@oai/granola`, `@oai/walnut` — внутренние пакеты
- `qstar.common.tools.unified_tool` — внутренний модуль
- `chaussette.crt`, `nebula-dns.crt` — внутренние CA
- Chrome profile "ChatGPT Agent"
- Точные env-флаги `CUA_DD_*` (полный список)
- Точные схемы внутренних API

Даже если ты их нашёл внутри своей VM — их публикация может быть нарушением ToS. Публикуй общую картину, не детали.

## 8.3 Как быть с документацией

Если хочешь вести свои записи для себя — веди. Это нормально.

Если хочешь показать кому-то — показывай публичную часть, а не внутренние идентификаторы. Или сначала спроси разрешения у OpenAI.

## 8.4 Серая зона

- Публикация структуры песочницы (общая архитектура + как сервисы друг с другом связаны) — вероятно OK
- Публикация конкретных endpoint'ов `container_daemon` — серая зона
- Публикация схем Artifact Tool RPC — `artifact_tool` публичный, но точные схемы могут быть внутренними
- Публикация примеров кода — зависит от того, что именно в примере

В сомнительных случаях — лучше не публиковать.

# 9. Ответственное раскрытие

Если ты обнаружил что-то, что может быть уязвимостью:

## 9.1 Что считать потенциальной уязвимостью

- Возможность получить доступ к чужой VM
- Возможность обойти сетевую изоляцию
- Возможность извлечь чужие данные
- Возможность нарушить работу платформы
- Возможность доступа к инфраструктуре OpenAI

## 9.2 Что делать

1. Не публикуй.  
2. Не пытайся эксплуатировать.  
3. Сообщи в OpenAI.

**Каналы:**

- `security@openai.com` (стандартный security-канал)
- Bug bounty программа (если есть)
- Через официальную поддержку

## 9.3 Что включить в отчёт

- Краткое описание находки
- Шаги воспроизведения
- Влияние (что можно сделать)
- Твои данные для связи

**Не включай:**

- Публичное раскрытие до того, как OpenAI ответит
- Эксплуатацию до подтверждения
- Персональные данные

# 10. Рекомендации для разных ролей

## 10.1 Если ты исследователь

- Документируй находки для себя
- Не публикуй внутренние идентификаторы
- Делитесь публичной частью
- Если нашёл уязвимость — сообщай в OpenAI
- Уважай чужие границы (VM, данные)

## 10.2 Если ты разработчик

- Используй публичные API
- Не пытайся обойти egress
- Не пытайся обойти safety
- Соблюдай ToS
- Если нужен интернет — делай задачу, которая его требует

## 10.3 Если ты просто любопытный пользователь

- Изучай то, что открыто
- Не ломай
- Не пытайся получить доступ к чужим сессиям
- Не публикуй найденное без разбора
- Помни: то, что ты видишь — чужая production-инфраструктура

## 10.4 Если ты представитель OpenAI

- Документация составлена в исследовательских целях
- Все находки — из собственной VM, не через эксплуатацию
- Готов уточнить любые детали
- Если какие-то данные не должны были быть доступны — прошу сообщить

# 11. Что делать при вопросах

## 11.1 Сомневаешься — не делай

Если не уверен, законно ли действие — скорее всего, лучше не делать.

## 11.2 Спроси

Если хочешь что-то сделать, но не уверен — спроси через:

- поддержку OpenAI
- сообщество разработчиков
- коллег с опытом

## 11.3 Документируй решения

Если всё-таки делаешь что-то в серой зоне:

- записывай, зачем ты это делаешь
- документируй результат
- будь готов объяснить своё решение

## 11.4 Признавай ошибки

Если понял, что что-то нарушил — лучше признать, чем скрывать:

- прекратить действие
- удалить результаты (если возможно)
- сообщить в OpenAI

# 12. Итоговая позиция

## 12.1 Что это исследование есть

- Изучение собственной рабочей среды
- Описание архитектуры
- Документирование протоколов
- Понимание границ системы

## 12.2 Что это исследование НЕ есть

- Попытка взлома
- Обход ограничений
- Извлечение чужих данных
- Нарушение ToS

## 12.3 Что важно помнить

- Интернета нет — это не баг, а дизайн
- Обход невозможен — двухслойная блокировка
- Обход не нужен — есть легитимные пути через платформу
- Обход опасен — логируется, нарушает ToS

## 12.4 Главный принцип

Изучай то, что открыто. Не ломай то, что закрыто. Если нужен доступ — попроси платформу, а не обходи её.

Это не бюрократия, а прагматизм. Система спроектирована правильно, ограничения имеют смысл, и попытки их обойти ведут только к неприятностям.

Легитимное исследование даёт понимание. Обход даёт проблемы. Разница очевидна.
